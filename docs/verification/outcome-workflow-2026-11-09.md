## 外部验证发现并修复的问题

首次推送的 [GitHub CI](https://github.com/nbcctwya/Selark/actions/runs/42643320842) 有 5/6 任务通过，Windows 3.11 在真实 TCP 验收的「队列已满应返回 429」断言失败；该任务此前的单元回归已通过。原始断言没有记录实际 HTTP 状态，因此不能精确还原当次调度。

本机向每次 HTTP 客户端创建注入 250 ms 开销，复现了同一行断言失败。原脚本在 400 ms 排队窗口内反复构建客户端/SSL 上下文，读取队列状态后到发起拒绝请求之间，队列可能已超时变化。修复是在计时场景开始前创建并复用线程安全的 HTTP 连接池，保留原有 400 ms 排队超时、429/Retry-After、零上游派发及真实落账断言，并补充失败时实际响应和在途状态。

慢客户端初始化进入常规回归，修复后的 32 项验收工具用例通过。该修复仅作用于测试器，没有放宽网关超时或改变运行时行为，也没有以重跑 CI 代替定位和修复。

## 成本、权限和后续行动

每轮闭环包含 3660 次直连/中转模拟上游处理、11 次运行约束模拟生成及 9 次恢复场景模拟处理，共 3680 次；三批合计 11040 次，**真实供应商请求和供应商计费均为 0**。三批采集墙钟合计 398.421 秒。回归、竞态重现实验和 GitHub CI 的计算时间另计，均使用合成环境，没有购买资源或增加生产常驻负担。

所有配置、服务和故障注入均在临时环境。工具只管理本次创建的进程组，不修改日常配置、不切换真实服务、不调节系统性能设置、不执行真实生成或部署。提交推送沿用会话中已有授权；将来真实调用必须另有具体费用上限和授权。

下一步由失败项决定：使用已有开发探针分别定位普通请求的文件同步、SQLite FULL 提交、线程调度及协议处理；再选择一个可验证的优化并做同环境前后对照。CPU/RSS 和 SSE 在本组通过，不能替代普通请求尾延迟的修复，也不能以降低持久性或放宽预算来消除失败。
