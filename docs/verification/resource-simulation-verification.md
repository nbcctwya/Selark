## 隔离方式与验证范围

测试使用四种真实适配器和共享的 Selark 鉴权、路由、并发、持久化实现，但连接全部新建在
临时目录，Key 全部为虚构值。Kimi 仍使用官方端点格式和现有安全检查，没有为测试放宽
生产配置限制；HTTPX MockTransport 拦截所有上游请求，没有真实 DNS/供应商网络回退。
模拟模式不作为生产服务选项暴露。

本机套接字验收中，HTTPX、独立 CLI 进程和标准库摘要示例通过真实 loopback HTTP 访问
临时 Selark 服务。它们不访问用户真实服务；配置和数据目录环境覆盖被清除。测试结束后
临时服务停止，临时配置、伪造令牌、模型用量和备份自动删除。

## 发现的问题与修复

0.6.0 在取得全局执行名额后才取得套餐名额。复现用例先占满全局执行名额，再从两个调用方
向同一套餐发请求：第二条请求继续等待，未及时返回套餐并发限制，违背“不额外积压套餐请求”的约定。
新增回归在修复前失败，其余最初的 57 个交叉案例通过。

0.6.1 将套餐名额预留前移到鉴权和用途检查之后、等待全局名额之前。单个套餐最多一个
在途请求，包含排队阶段；第二条请求明确返回 429。若等待期间别名目标改变，调度前重新
核对并释放或获取对应套餐名额。沿用原有 finally 清理，取消、等待超时、停用和权限拒绝
不会遗留名额；不更改普通 API 的并发语义，也不增加上游生成重试。

## 重复运行

开发环境中执行：

```bash
.venv/bin/pytest -q
.venv/bin/ruff check .
.venv/bin/ruff format --check .
.venv/bin/python scripts/verify_resource_matrix.py --output /tmp/resource-matrix.json
```

也可在仓库外、未激活开发环境时，使用已经安装的 0.6.1：

```bash
"$HOME/.local/share/pipx/venvs/selark/bin/python" \
  /absolute/path/to/Selark/scripts/verify_resource_matrix.py \
  --selark "$HOME/.local/bin/selark" --output /tmp/resource-matrix.json
```

脚本固定创建临时环境，不接受真实 Key、真实连接 URL 或现有服务地址。需要保留仓库中的
测试 fixture，这是验收脚本的依赖，不是日常 `selark` 运行的依赖。
GitHub Actions 已加入该矩阵，Python 3.12 执行套接字测试，三个 Python 版本执行全部回归；
本轮未推送或触发远程 CI。

## 安装与限制

当前 WSL 用户的非 editable pipx 安装更新为 0.6.1；27 个 Python 源文件与已验证实现一致，
`pip check` 通过。仓库外的新终端直接运行 `selark --version` 返回 0.6.1。
安装及安装版本验收前后，10 个实际私有配置/数据库文件哈希相同。
无需配置或数据库迁移；真实服务始终未启动，临时服务均已停止。没有执行系统级安装。

结论限于 Selark 在模拟供应商行为下的路由、并发、故障与计量表现。真实厂商的限流阈值、
模型可用性、套餐实时额度及其网络行为没有新增验证；本轮没有为此产生真实费用。
