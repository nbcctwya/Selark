## 桌面生成请求 400 修复验收

用户随后报告两个桌面端均可列出模型，但生成返回本地 `invalid_request`。请求日志确认在上游派发前失败。通过本机 DSH 0.2.1-rc.5 打包的 pi-ai 1.3.0 实际序列化代码，复现了 `store:false` 被拒绝；隔离运行 Kimi CLI 0.42.0，复现了 `prompt_cache_key` 被拒绝。它们属于 [官方 Chat 请求字段](https://github.com/openai/openai-python/blob/main/src/openai/types/chat/completion_create_params.py)，此前 Selark 的严格字段列表遗漏了这些选项。

- 增加 `store`、`prompt_cache_key`、`prompt_cache_retention` 的类型校验及同协议转发，保留调用方的值，不增加提示文本、模型派发或本地缓存。Anthropic Chat 转换对无法映射的存储/缓存选项明确报错，避免静默丢弃语义。
- 参数错误现在包含已知字段位置和校验类型，日志最多记录 8 项；不输出输入值、正文、凭据或任意未知键名。扩展既有校验和工具循环测试，完整回归 **877 通过，91.06 秒**；Ruff、格式、敏感信息及契约检查通过。
- 最终隔离客户端联测使用模拟上游：Kimi 经 Selark 收到 `Read` 工具调用、读取临时文件、回传工具结果并完成回复；DSH 自带的 pi-ai SDK 经 Selark 收到完整流式回复。合计 3 次模拟派发。此项使用 Kimi CLI 和 DSH 打包 SDK，未操作用户正在使用的桌面会话。
- 更新日常 pipx 安装并重启核心服务；54 个 Python 文件与源码一致，依赖检查通过。Windows 经原地址访问 `/health` 成功。个人应用权限、桌面配置和开机自启设置保持原样。
