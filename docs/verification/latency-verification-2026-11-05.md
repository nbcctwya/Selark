# 全链路延迟验收 · 2026-11-05

本轮先测量鉴权、配置/路由、配额事务、HTTP 收发、交付和持久结算，再合并线程往返与派发前事务。修正测量条件后的同环境对比：普通请求 p95 额外延迟 **14.99 → 13.42 ms，下降约 10.4%**；SSE 首段 **9.61 → 8.21 ms，下降约 14.5%**。普通响应仍未达到 10 ms，保留原目标。

## 测量条件修正

原测量器的直连客户端设置 `trust_env=False`，临时核心则继承系统代理。本机 `NO_PROXY` 包含 `127.*`，HTTPX 未按预期匹配；检查实际传输对象确认为 `AsyncHTTPProxy`，两条路径不等价。本轮修改前按旧条件复测的三个 p95 中位数是普通 21.39 ms、SSE 首段 16.49 ms，不能视作纯本机中转开销。

现在只为测量用临时进程设置 `NO_PROXY=no_proxy=127.0.0.1,localhost,::1`，正式服务的代理行为不变。11 月 4 日的历史报告未记录实际代理路由，不能排除此影响，也不能据此断定当时两次超时的原因。本轮重新建立基线；移除代理的差额不计入代码优化收益。

基线代码为 `d1d25c1`，使用修正后的同一测量器。Python 3.12.2、Linux/WSL、单请求并发、Dashboard 关闭、单个普通 API 连接，默认限流及完整鉴权/配额/日志/SQLite/恢复流程。每轮普通与 SSE 各 300 对、预热各 5 对，610 次中转结束后测空闲 30 秒。参考采样期间不运行其他构建、测试或真实 API 调用。

## 实际改动与完整链路

1. 入口仍先鉴权，再接收/解析请求体，读取路由、应用策略并进入有界队列。
2. 每轮路由把资源与连接配置的读取放在一次工作线程调用中。排队后仍重新读取路由/策略；派发前仍在配置锁内复查模型批准状态，并在 SQLite 事务内复查撤销、权限、并发和配额。不缓存授权结果。
3. 将请求登记、配额预留和派发意图合为一个 `synchronous=FULL` 事务，提交成功后才调用上游。原来的独立登记事务及一次线程往返被移除。更早的拒绝或取消由既有 `finish` 插入路径收尾；崩溃发生在该事务之前时尚未派发生成，也没有已派发费用需要恢复。
4. HTTP 调用、内容/用量校验和普通/SSE 交付保持原有逻辑。每个接纳请求至多派发一次，不增加提示、补写历史或自动重试。
5. 检查点和最终结算分别在收据工作线程一次完成连续工作：原子写收据、文件/目录 fsync、SQLite FULL 提交、必要的收据删除与目录同步、积压计数。保留原顺序；SQLite 互斥锁串行保护与数据库查询线程共享的连接，收据同步期间查询仍可进行。恢复事件通过线程安全回调唤醒事件循环。

上游完成后的检查点仍在普通响应/终止 SSE 事件送出前持久化；交付后再次结算实际交付状态。文件与数据库故障、取消、旧收据重放、备份和重启恢复均保留。没有新增常驻线程、缓存、轮询或进程。

开发探针只由 `measure_relay --profile` 在临时进程安装，正式运行不导入。探针记录时间与操作名称，不记录消息、答案、API Key 或配置内容；其结果不用于预算判定。

## 三轮无探针对比

以下是三个独立 p95 的中位数，不是合并样本的 p95；每轮使用逐对有符号差值和 nearest-rank 百分位。

| 指标 | 修改前 | 修改后 | 预算/结论 |
| --- | ---: | ---: | --- |
| 普通完整响应 p95 额外延迟 | 14.9866 ms | 13.4208 ms | ≤ 10 ms，仍未达标 |
| SSE 首段文本 p95 额外延迟 | 9.6058 ms | 8.2086 ms | ≤ 10 ms，三轮均通过 |
| SSE 完成 p95 额外延迟 | 14.4031 ms | 14.0434 ms | 单独观察，改善约 2.5% |
| 核心空闲 RSS 中位数 | 66.20 MiB | 62.23 MiB | ≤ 72 MiB；修改后三轮 62.09–65.84 MiB |
| 空闲 CPU，单核 | 约 0.10% | 约 0.13% | ≤ 0.5%，没有 CPU 下降的证据 |

修改后的三轮普通 p95 分别为 13.4208、13.9124、12.4450 ms，SSE 首段分别为 8.2086、8.4566、7.6373 ms。严格模式三轮均返回 1，唯一未达标项为普通响应延迟。每轮额外生成 0、空闲上游调用 0、完整负载不变、610 条中转记录、8,540 个合成 Token、退出后 pending 清空。

80 对/模式的探针样本显示，鉴权结束至派发上游这段的 p50：普通 **5.72 → 4.20 ms**，流式 **5.66 → 3.53 ms**。交付后结算 p50：普通 **8.01 → 7.26 ms**，流式 **8.12 → 7.77 ms**。普通响应从上游头到本地正文的 p50 仍约 4.7 ms，包含正文读取/校验和持久检查点；磁盘同步的尾延迟仍明显。各段分布不能相加为总 p95；嵌套 HTTP body span 还可能包含迭代器暂停期间的下游交付与落账等待。

## 经用户授权的真实 API 小样本

只使用 MiMo `mimo-v2.6-flash`、OpenAI `gpt-6-luna`、已有中转站 `claude-sonnet-4-6`。每个连接普通/流式各一次直连和一次中转，共 **12 次生成尝试**；输出上限分别为 16、64、16。没有重试、模型切换、OAuth、目录发现或修改真实配置。凭据仅在内存中使用，本机服务和账本均隔离。

12 次协议与记账检查完成：全部原始发送负载与预期一致，6 次中转均只派发一次、正确保存返回用量，pending 为零。供应商共报告 **224 Token**，包含直连与中转及真实推理计数，不按估算价格宣称实际费用。OpenAI 仅调用 Luna；本轮直连/中转均报告 11 个输入 Token，输出和推理计数随生成变化。

这些是连通性和链路定位小样本，没有足够样本计算真实 API p95，也不能将两次真实模型调用的耗时差直接视为 Selark 开销。

| --- | ---: | ---: | ---: |
| MiMo | 12,392.88 ms | 13,510.07 ms | 3.05–6.27 ms |

MiMo 两次中转出现长等待：普通请求约 8.07 秒等待上游响应头、4.31 秒处于上游正文读取；SSE 约 5.06 秒等待上游响应头，头部至首段本地正文约 8.44 秒。已定位到 HTTP 等待区间，未进一步区分供应商与网络/代理原因，不归入本地路由耗时，也未为获得更快样本重试。

**回答质量没有全部通过**：MiMo 与 Luna 的 8 次均返回期望的 `OK`；中转站 3 次有文本但不严格符合 `OK`，另一次直连 SSE 完成却无文本，其首段时间记为 `null`，不是 0 ms 或低延迟成功。中转站该次供应商报告 15 个输入、0 个输出 Token；按原值保留，不隐藏异常。这不作为本次本地优化的速度收益。
