1. **SEC-01：Dashboard 会话没有按端口隔离。**

   位置：[dashboard.py](../src/selark/dashboard.py)，第 97、126–127、166–168 行。
   管理员会话以 `HttpOnly; SameSite=Strict; Path=/` Cookie 保存，Cookie 名称带有端口。
   Cookie 的浏览器作用域不区分端口，名称含端口不会改变这一规则。
   当用户登录面板后，在同一浏览器中访问另一个 `http://127.0.0.1:端口/` 服务，
   浏览器会把这个管理 Cookie 发送给该服务；接收方可以用自己的 HTTP 客户端重放。
   这符合 [RFC 6265 第 8.5 节说明的端口隔离限制](https://www.rfc-editor.org/rfc/rfc6265#section-8.5)。

   使用 Chromium 149.0.7827.55、两个临时 TCP 服务和一次性浏览器上下文验证：
   正常登录返回 200；另一个端口实际收到了 Cookie；随后重放访问 `/api/snapshot` 返回 200，
   请求 `/api/model-approval` 也返回 200，并禁用了临时配置中的合成模型。
   会话值仅在内存中使用，没有保存到报告或日志。

   触发前提是同机有不可信 HTTP 服务，用户在管理会话有效期内访问该服务。
   本轮没有证明普通远程网页能直接绕过同源检查，也没有证明能读取上游 API 密钥。
   当前 Host、Origin、Fetch Metadata 和自定义请求头检查对浏览器跨源请求仍有价值；
   但 Cookie 已被服务端拿到以后，重放方可以自行设置这些请求头。

   建议将管理凭据改为按 origin 隔离、由前端显式放入请求头的会话令牌，
   可保存在页面内存或按 origin 隔离的 sessionStorage 中，并保留现有同源、CSP、过期和一次性登录保护。
   修复验收应包含真实浏览器跨端口访问，确认其他端口收不到管理凭据，以及模型管理功能仍正常。

2. **SEC-02：鉴权晚于共享准入和请求体读取。**

   位置：[app.py](../src/selark/app.py)，第 180–192、251–273 行；
   [admission.py](../src/selark/admission.py)，第 42 行起。
   生成请求先执行 `gate.reserve()`，再读完请求体，最后在 `process()` 中验证 Authorization。
   因此没有令牌的连接也能占用 `max_active + max_queued` 个共享名额。

   临时网关使用默认容量 4 个运行名额和 16 个排队名额。
   为缩短复现时间，只把读取请求体超时从默认 10 秒改为 3 秒。
   20 个没有 Authorization 的 TCP 请求各只发送一个字节的请求体并保持连接：
   `/health` 显示 `active=0, queued=0, admitted=20`；合法请求从 200 变成
   429 `server_overloaded`；关闭这些连接后，合法请求恢复 200。
   两次合法请求共调用模拟上游 2 次，匿名请求没有派发上游。

   服务默认仅监听 loopback，风险是本机可达范围内的可用性问题。
   有请求体超时意味着占用不是永久的，但持续补充慢连接可重复占满名额。
   另外，这 20 个匿名失败请求都写入了账本；应把匿名失败记录的容量和保留策略一起纳入设计。
   本轮没有进行填满磁盘的测试，也不据此宣称已复现磁盘耗尽。

   建议在生成任务准入和读取完整请求体之前检查认证头及身份，
   给认证前连接设置独立的有限容量，避免把拥塞转移到认证存储队列。
   保留请求体大小、超时、调用方并发以及派发前权限复查。
   验收应覆盖匿名慢请求与合法请求并发、无效或重复认证头、令牌撤销、队列清理及落账边界。

3. **DEP-01：构建依赖版本落后于安全修复。**

   位置：[requirements.lock](../requirements.lock)，第 20 行，`setuptools==82.0.1`；
   [pyproject.toml](../pyproject.toml)，第 2 行，构建要求 `setuptools>=75,<83`。
   本轮测试虚拟环境安装的版本也是 82.0.1。
   对所有 `requirements*.lock` 的 32 个不同固定依赖查询 OSV，返回 3 条记录，
   按别名去重后是 setuptools 的 2 个公告；其余 31 个依赖未返回匹配公告。

   macOS 上构建 sdist 时，Unicode 文件名规范化差异可能使 MANIFEST.in 排除规则失效，
   导致应被排除的文件进入发布包。公告为
   [GHSA-h35f-9h28-mq5c / CVE-2026-59890](https://github.com/pypa/setuptools/security/advisories/GHSA-h35f-9h28-mq5c)。
   OSV 和 [setuptools 83.0.0 官方变更记录](https://setuptools.pypa.io/en/latest/history.html#v83-0-0)
   标明 83.0.0 已修复；公告页的 Patched versions 字段仍显示 None，应以修复记录交叉核对。
   当前仓库未发现 MANIFEST.in，本轮在 Linux 环境检查，没有发现本项目发生此类打包泄露的证据。

   Windows 旧式 wheel 安装路径可被恶意 namespace_packages.txt 引导到目标目录外创建
   固定内容的 `__init__.py`，公告为
   [GHSA-xmj3-9gf7-h52w](https://github.com/pypa/setuptools/security/advisories/GHSA-xmj3-9gf7-h52w)，
   修复版本为 84.1.0。官方变更记录说明该路径仅由弃用的、位于 PEP 517 前端之外的
   setup_requires 机制触发，setuptools 构建后端不会走到该路径。
   参考 [84.1.0 官方变更记录](https://setuptools.pypa.io/en/latest/history.html#v84-1-0)。
   这两项不能直接解释为 Selark HTTP 网关存在远程代码执行漏洞。

   建议在隔离环境验证至少 84.1.0 的受支持版本，并同步调整构建范围与锁文件，
   验证 wheel/sdist 内容、干净安装和 Python 3.11–3.13 的 CI。
   当前 `<83` 上限会阻止解析到上述修复版本。
   [现有 CI](../.github/workflows/ci.yml) 有凭据扫描和功能回归，可补充依赖漏洞查询；
   `pip check` 只检查依赖兼容性，不能代替漏洞检查。

4. **PERF-01：每日配额检查随当天请求数量线性增长。**

   位置：[governance.py](../src/selark/governance.py)，第 243–263、355–359 行；
   [storage.py](../src/selark/storage.py)，第 474 行起。
   设置每日 Token 或费用配额后，每次派发会读出同一调用方当天的全部 allocation，
   关联请求用量，解析 JSON，再做一致性检查和汇总。
   查询已使用 `allocations_day` 及请求主键索引，但匹配到的全天明细仍需逐条处理。
   这段工作位于 SQLite 写事务中，且运行时数据库执行器只有一个工作线程。

   以下为临时文件数据库、已正常结算的合成记录、开启 daily_token_limit 时，
   实际 `Store.attempt()` 的 5 次测量中位数。每次测量前后的建档和清理不计入耗时。

   | 同一调用方当日已有记录 | 单次准入检查中位耗时 |
   | ---: | ---: |
   | 0 | 1.320 ms |
   | 1,000 | 12.656 ms |
   | 10,000 | 115.983 ms |
   | 50,000 | 590.551 ms |

   这是当前机器的本地存储基准，不含模型网络延迟，也不代表当前真实账本已有此规模。
   建议按调用方和日期维护可校验的增量汇总，在预留、结算和恢复事务中一起更新；
   必须保留未知用量暂停、历史矛盾用量重校验和金额精度规则，不能简单删除逐条校验而放松预算。
