# 资源占用与转发开销

Selark 的目标是低开销的本机转发与管理。常规中转不会追加模型输入，也不会为了转发再调用一次模型；具体约束如下。

这些要求已纳入 [硬性设计原则与性能预算](../development/design-principles.md)，并写入两个仓库的 `AGENTS.md`，适用于日常开发、Claude 前端交接及未来桌面版。

## 中转的 Token 边界

- 只发送调用方提交的消息；保留文本、空白与顺序。不追加 Selark 的系统提示、摘要、翻译、心跳文本或验证问题。
- `session_id` 只用于本机归组，不发送给供应商，也不据此存储、读取或自动拼接对话历史。
- 每个接纳的生成请求最多派发一次上游生成；限流、超时、协议错误或断开后不会自动重试、补答或切换模型。账本恢复只恢复本机记录。
- 健康检查、页面刷新、历史与配额统计不生成文本；显式模型发现查询目录。CLI `model verify` / `connection probe` 是用户明确发起的生成测试，会消耗供应商用量。
- 输入估算、输出预留及费用计算都在本机完成，不调用模型或远端分词服务，不把估算值加进上游消息或真实用量。最终用量以供应商报告为依据，未知保持未知。

这保证的是 **Selark 不增加提示文本和生成次数**，不是跨供应商、跨协议的 Token 数完全相等。适配 Anthropic Messages、Responses 等协议时需要转换角色与字段；供应商如何计算消息结构、缓存和推理 Token 由其决定。模型自身的推理仍属于该模型的消耗，例如 Kimi Code 的思考模式；Selark 不通过额外提示词模拟不支持的参数。调用方自行重试也是新的请求。

## 降低常驻占用

网关、Dashboard 与命令行管理可以独立使用。只需转发时运行 `selark serve`；Dashboard 按需打开，用完后关闭其终端中的进程。正式安装提供已构建的静态页面，日常使用不需要 Vite 或 Node 服务。

已实现的限制和优化：

- 空闲时，恢复协程等待事件，不再每秒读取恢复目录。发现积压或写入故障后自动唤醒，每秒最多恢复 8 条，清空后继续等待；保留每次请求的持久落账和重启恢复。
- JWT 与密码学验证依赖延迟到 OAuth 身份验证时加载；普通 API 转发、状态读取与本地备份无需提前加载它们。
- 页面更新时间只重绘时间标签；隐藏标签页停止时间计时和自动读取，返回时更新。可见时仍按原有 30 秒周期刷新；编辑弹窗、输入中、离线或读取尚未完成时暂停自动读取。
- 继续复用上游 HTTP 连接池；默认最多 4 个并发生成和 16 个排队请求。请求体、响应与 SSE 事件有大小上限；Chat Completions 逐块转发，Responses 保留有界文本缓存用于核对完成事件。
- 每轮路由的资源与连接配置在一次工作线程调用中读取；排队后的重新路由、派发前的锁内审批与配额复查仍保留，不缓存授权状态。
- 请求登记、配额预留与派发意图合并为一次同步事务；检查点和最终落账分别在一次工作线程调用中连续完成，保留文件/目录 fsync、SQLite FULL 同步和原有恢复顺序。

CPU、内存和磁盘写入不会为零。Python/HTTP 服务、连接、配额检查与可靠落账都有必要开销；不通过关闭落账、减少权限复查或丢失用量来降低数字。

## 测量与回归

在开发环境可运行：

```bash
python scripts/measure_runtime.py --idle-seconds 10 --requests 100
```

脚本使用独立临时配置和内存模拟上游，不读取个人配置、不监听端口、不访问真实供应商。预热一次，然后测量空闲和 100 次顺序请求；断言上游消息不变、每次请求只产生一次模拟生成、用量不重复累计。RSS 目前从 Linux `/proc` 获取，其他平台输出 `null`。

对比时使用相同 Python、依赖、机器和脚本，各版本分别启动新进程。报告包含同进程的模拟调用方与测量工具，不是实际部署的最低内存承诺；小量 CPU 时间及磁盘耗时有波动。测量记录见 [2026-11-04 验收](../verification/efficiency-verification-2026-11-04.md)。

本机 TCP 额外延迟及核心进程预算单独测量：

```bash
python -m scripts.measure_relay --output /tmp/selark-relay-budget.json
# 固定参考环境的严格验收：任一预算未达到或不可测，保存报告后返回非零。
python -m scripts.measure_relay --check-budget --output /tmp/selark-relay-budget.json
```

默认每种模式 300 对样本、各预热 5 对，再测 30 秒核心空闲状态；所有调用均为回环模拟。每对交替直连/中转次序，输入参数与上游响应一致，使用 HTTP keep-alive 并禁用模拟服务器的 Nagle 延迟。普通响应统计完整正文接收，SSE 统计第一段真实文本并另报流完成时间。以逐对差值计算 p50/p95/p99，保留负差值和全部样本；不减去两个独立的 p95。

测量器为临时核心设置明确的回环 `NO_PROXY`，避免环境里的 `127.*` 等模式在 HTTPX 中未匹配、使中转绕行系统代理。本轮已复现原脚本绕行代理；11 月 4 日的报告没有记录代理路由，不能排除此影响，保留为历史证据。当前优化必须与修正路径后的同环境基线比较，不能把移除代理的差额算作代码收益。这不改变正式网关访问外部供应商时的代理设置。

定位全链路瓶颈时可显式开启开发探针：

```bash
python -m scripts.measure_relay --samples 80 --idle-seconds 1 \
  --profile /tmp/selark-relay-stages.jsonl --output /tmp/selark-relay-profile.json
```

探针只安装到本次临时进程，记录鉴权、派发前检查、上游响应头、首个 ASGI 正文、交付结束及结算时点，并细分配置、线程排队、HTTP 和持久化操作。不保存请求/回复内容或凭据。`phases_ms` 是各段本身的分布；`inclusive_spans_ms` 可能嵌套，不能相加各段 p95。首个 ASGI 正文未必包含文本，正式首段文本延迟仍由客户端解析 SSE 计量。探针会引入开销，不能与 `--check-budget` 合用，正式预算使用未插桩的新进程。

最新前后对比及真实 API 小样本见 [全链路延迟验收](../verification/latency-verification-2026-11-05.md)。
追加的 440 次真实 API 顺序/并发观察、空回复和供应商计数差异见 [多轮验收](../verification/live-latency-rounds-2026-11-05.md)；真实上游时间与本机预算分别解释。

参考预算暂设参考批次后的空闲核心 RSS 72 MiB、单核空闲 CPU 0.5%、普通与流式首段的 p95 额外延迟 10 ms。预算用于跟踪回归；未达标会直接出现在 `budget_checks` 中，不能将报告生成成功视作性能达标。共享 CI 采用较短样本产出报告，并执行确定性的调用次数、消息保真、落账与空闲扫描约束，不用共享机器的时延决定合并。

性能采样单独作为非阻断步骤：超时等测量失败会覆盖旧报告，保留错误类型、阶段、部分样本及可用日志，不能显示为 0 ms 或“达标”；功能回归与确定性检查仍阻断 CI。参考基线和校准异常见 [设计预算验收](../verification/design-budget-verification-2026-11-04.md)。
