# 六类应用场景、多轮与并发真实验收（0.6.2）

日期：2026-10-29；WSL/Linux，当前用户非 editable pipx 安装。
本轮新增 **117 次真实上游生成请求/尝试**，与此前的 8 次短请求、32 次长文本请求分开计数。
所有生成经过 Selark HTTP；没有用模拟回答补齐真实结果。

**MiMo、DeepSeek、Kimi 均完成六类场景的三轮对话。中转站六类均已尝试，但未完成三轮验收：
其普通响应、流式响应及极短诊断反复出现上游错误，不能报告为通过。**

证据：[逐请求结果与用量](application-live-verification.json)、
[24 份实际回答样本](application-live-samples.md)、
[原创场景与检查规则](../scripts/application_scenarios.py)。
这些材料不含凭据或思考正文；回答中的项目、人物与数据均为虚构测试材料，没有发送本地私有源码。

## 覆盖范围

原计划：三个按量 API 各六类 × 两个案例 × 三轮，Kimi 六类 × 一组 × 三轮，共 126 次。
中转故障发生后停止原调度，另行进行有界诊断和显式补测；这些是新增请求，不覆盖失败记录。
最终完成 **30 组完整三轮对话**，不是把三个独立问题算成三轮。

| 场景 | MiMo | DeepSeek | Kimi Code | 中转站实际成功轮次 |
| --- | --- | --- | --- | --- |
| 情绪/语气分析 | 2 案例 × 3 轮 | 2 × 3 | 1 × 3 | B 第 1 轮；后续失败 |
| 翻译 | 2 × 3 | 2 × 3 | 1 × 3 | B 第 1 轮；后续失败 |
| 编程 | 2 × 3 | 2 × 3 | 1 × 3 | B 第 1、2 轮；未完成第 3 轮 |
| 写文章 | 2 × 3 | 2 × 3 | 1 × 3 | A、B 各第 1 轮；不是一组两轮 |
| 聊天与个人计划 | 2 × 3 | 2 × 3 | 1 × 3 | B 第 1 轮 |
| 项目设计 | 2 × 3 | 2 × 3 | 1 × 3 | B 第 1 轮 |

这里的“完成”指链路交付结束；内容正确性另行检查，包括一次 `finish_reason=length`。
每次续问都携带该模型此前真实回答。Kimi 前两轮还原样带回实际 `reasoning_content`，
第三轮使用流式输出；没有编造思考、自动拼接服务器历史或借用其他模型的回答。

## 并发与中转故障

第一批普通 API 客户端并发上限 3，Kimi 单独交互；观测服务同时执行峰值 **4**，排队峰值 0。
966 次健康采样失败 0，最大耗时约 **4.60 ms**，未观测到存储降级。此批普通 API 请求使用
两名既有调用方，Kimi 使用自己的授权令牌；服务端记录身份与实际鉴权一致。

中转补测先使用并发 2；连续超时后停止调度，两个在途请求按客户端取消落账，资源释放。
审阅到另两条在途请求已成功且 `/models` 可读后，显式尝试单并发，首个 400 后立即停止。
随后独立选择同连接原允许列表中的 `claude-sonnet-5`，首个请求也返回 400，停止该组。
默认模型、连接配置和 Selark 自动路由均未改变，没有自动切换来源或重试生成。

中转 19 条未完成记录为：

- 7 条 `upstream_protocol_error`：上游返回了不符合文本 Chat Completions 协议的响应。
- 7 条 `upstream_timeout`：等待或读取上游超时。
- 2 条 `client_disconnected`：为停止持续故障补测，主动取消仍在执行的请求。
- 3 条 `upstream_rejected`：上游 HTTP 400，Selark 返回明确的 502 错误。

最后单独发送 `Reply only OK.`、输出上限 32，仍得到上游 400，错误类型为 `server_error`，
错误正文说明其上游返回 `bad response status code 400`。Selark 请求 ID 为
`d93d6603650c446e954b0312741d7681`。只读 `/models` 在约 507 ms 内列出 8 个模型且包含原模型，
说明模型列表可读**不能证明生成路由可用**。现有信息不足以判断内部账户、路由或模型服务的具体原因；
需要中转站确认生成路由恢复后才能补齐三轮验收，不能用模拟结果代替。

## 答案检查

按本轮明确的字段、引用、字数、结构及代码检查：**77 条通过、21 条未通过、19 条不评估**。
这不是通用能力排行榜，也不等同于对全部语言与工程细节的认证。重点发现：

1. 语气标签大多可随上下文更新，但几家模型把要求的“连续原文证据”改写或拼接，不能作为逐字引用。
2. MiMo 的聊天 B 前两轮在 JSON 外添加引导语，违反纯 JSON 要求；第三轮改为合法 JSON。
3. DeepSeek 的设计 A 三轮新增了未要求的根字段；结构可解析但违反“恰好五个根字段”。
4. 部分文章没有遵守汉字数区间。统计仅计算汉字，不包括数字、标点和 Markdown。
5. MiMo 设计 B 第三轮达到 2,048 输出上限，JSON 截断；保留 `length` 和全部实际用量，未伪装为合格答案。
6. Kimi 文章和设计有需要人工纠正的事实/工程细节；反馈后修正。这说明多轮审阅有价值，
   不能仅凭 HTTP 200 或字段齐全就认定文章、架构正确。

实际执行 **17 个函数版本、4,479 项检查，全部通过**。校验器见
[check_application_code.py](../scripts/check_application_code.py)：先限制 AST、导入和调用，
再用独立进程、有限 builtins、CPU/内存/文件写入限制执行。它只用于这两个明确的练习，
不是通用安全沙箱；应继续放在受限环境中运行。

验收器也经审阅修正了几项过窄假设，均只重评本地结果、没有新增模型调用：

- 无上下文的简短应答允许 `neutral` 或 `unclear`；补充明确失望语境后仍严格要求 `negative`。
- 文章第二轮允许明确指出旧值并说明更正；只有第三轮明确禁止旧值再次出现。
- 设计提示未强制 `constraints` 为对象，因此人工检查五条数组表示。四条保留所需约束；
  一条未明确保留禁止自动切换收费来源，仍判未通过。
- CLI 返回的额外顶层缓存计数与标准用量字段先统一归一化再比对；保留原值，不重复累计。

## Kimi 用途扩展与本地配额

用户明确授权扩大为个人交互式翻译、写作、聊天等任务；已再次核对
[Kimi Code 使用规范](https://www.kimi.com/code/docs/kimi-code/community-guidelines.html)。
新增 `plan.use=personal_interactive`、CLI `--interactive`、HTTP `interaction=personal_interactive`，
记录用途 `interactive_task`。旧连接默认仍是编程用途，旧 `--interactive-coding` 继续可用。
普通令牌不因此获得套餐权限，CLI 要求交互终端，使用真实 Selark User-Agent。

18 次 Kimi 请求逐次触发并审阅，没有纳入 API 批量调度；每次仍查询官方额度、确认不使用加油包，
连接并发 1、每分钟 4 次的限制保持。没有自动切换到额外付费来源，未从本地 Token 推算套餐余量。

为了避免 512 输出上限只够思考，验收期间暂将输出上限设为 2,048、输入估算上限 20,000、
本地日限额 80,000；**结束后已恢复原来的 512 / 4,000 / 10,000**，其余权限始终不变。
已显式授权的个人用途扩展保留。

**恢复后，2026-10-29 这个 UTC 日的 Kimi 本地累计为 32,463，超过原 10,000 日限额，
因此当天新的 Kimi 调用会被本地额度限制。** 这不是官方套餐耗尽的判断。
原策略按 UTC 日重置，下一次为北京时间 2026-10-30 08:00；本机所有者也可主动修改自己的策略。
