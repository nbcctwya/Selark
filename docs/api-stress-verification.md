# Selark 0.4.1：API 极端场景与并发追加验收

执行日期：2026-10-28，WSL/Linux。基于 0.4.0 增加压力与异常数据测试，修复测试实际发现的问题，
将验证后的 0.4.1 更新到当前用户 pipx。真实连接、凭据、运行限制、调用方令牌与撤销状态均未修改。

本次新增 **8 次真实请求，无重试：7 次完整成功、1 次主动取消**。
已知用量为输入 128、输出 17、合计 **145 tokens**；取消请求未取得最终用量，保持未知，不能把 145 当作本次完整消耗。
这与 [上一轮 0.4.0 的 6 次、129 tokens](multiconnection-verification.md) 分开统计。

## 新发现及修复

先加入测试复现，修复前 8 个用例失败、2 个通过。实际发现三类问题：

| 问题 | 修复前行为 | 0.4.1 行为 |
| --- | --- | --- |
| 没有换行的超长 SSE 数据 | HTTPX 先缓存整行，直到结束才进入大小检查；测试中读完 80 个 64 KiB 块后才拒绝 | 读取片段时检查行的字节数，在第 17 块达到超出 1 MiB 的位置拒绝并关闭上游，不继续读完。MiMo/兼容及 Anthropic 适配共用实现，CLI 也使用相同的有界拆行。 |
| 上游过深 JSON | 普通和流式路径抛出未处理的 RecursionError | 转为可记录的 upstream_protocol_error，普通响应 502，已开始的流发送 error 事件，无成功 DONE。解析后的结构最多 64 层。 |
| NaN、Infinity 和溢出指数 | 普通响应序列化异常；流式可能转发非标准 JSON 并成功结束 | 上游 JSON 统一拒绝非有限数字，包括 1e999；按协议失败收尾，名额释放，不重试生成。模型发现也使用相同解析。 |

追加测试还覆盖多字节 UTF-8、BOM、跨片段 CR/LF/CRLF、多个空 data 字段的事件大小限制，
100 次重复累计/仅用量 SSE 片段、零值与未知值、超过 SQLite 64 位范围的单项计数，以及汇总超过该范围时不溢出。
过大计数保留原 reported_usage，但不能写入标准整数字段的值保持未知，不截断为零。

## 模拟和本地 TCP 压力结果

最终自动回归：**205 项通过**，原有 187 项保持通过，新增 18 项；Ruff 检查及 49 个 Python 文件格式检查通过。
唯一警告仍是 Starlette TestClient 对 httpx 的弃用提示。所有自动测试使用临时配置、存储和虚构凭据。

[压力脚本](../scripts/verify_api_stress.py) 用实际本地 TCP 启动 Selark 和模拟上游，配置 4 个执行名额、8 个排队名额。
开发版本与最终安装版本各执行一次；下列数字来自**最终安装版本的一次验收**，见 [原始结果](api-stress-local.json)。

| 场景 | 实际结果 |
| --- | --- |
| 三轮突发，每轮 80 个同时请求 | 每轮 12 个 HTTP 200、68 个 HTTP 429，拒绝含 server_overloaded 和 Retry-After；每轮仅 12 次模拟上游生成，上游峰值始终为 4。 |
| 两个调用方、两个连接交叉使用相同模型和会话名 | 每条成功记录与请求的令牌身份、实际连接对应，用量各 14；没有错误归属或重复落账。 |
| 执行中 4 个、排队 8 个一起断开 | 12 条取消记录，只有执行中的 4 条发生上游尝试，其余没有生成；所有最终用量未知，名额全部释放。 |
| 排队期间撤销令牌、停用连接 | 已通过鉴权的旧请求继续；同令牌新请求 401。排队连接停用后返回 503，未发上游。全部操作限临时配置。 |
| 10 个错误或慢请求 | 空/过多 messages、无效 token 上限、自报调用方、未知连接/模型、错误 stream 类型、超过 1 MiB 请求体、重复 Authorization、慢请求体均明确拒绝，没有新增上游调用。 |
| 4 条流输出期间持有 SQLite 写锁 | 每条收到 40 个内容事件、最终用量事件和 DONE；锁住时仍持续输出。新的分发返回 503，未生成。 |
| 写锁期间落账、备份与重放 | 观察到 4 份待落账文件；运行中备份恢复出完整 56 tokens，二次重放不增加用量；解锁后原库恢复成相同计数。 |
| 全部故障后继续调用 | 新请求成功，执行/排队/接纳数为 0，pending/invalid 为 0，停服后恢复命令无需修复。 |

最终这一轮共 **275 次客户端 Chat API 请求、50 次模拟上游请求**。
保存 71 条记录：46 成功、12 取消、13 本地失败；204 次过载拒绝按现有设计只记请求日志，不新增落账。
已知模拟用量 644 tokens，全在临时库，不进入真实统计。突发期间抽样 health 响应约 1.88–2.25 ms，
SQLite 写锁期间抽样约 1.99 ms；这些是本次观测，不是吞吐或延迟承诺。

付费验收脚本还先使用临时本地假上游完整试跑，8 次模拟请求通过，确认并发峰值 4、排队峰值 2、断开后取消。
此试跑同样没有使用真实配置或生成。

## 真实并发与边界调用

使用已安装 0.4.1，通过 Selark HTTP 服务发起，工作目录在仓库外，未激活开发虚拟环境。
复用 legacy 与已有活动调用方两个令牌，不创建或撤销真实令牌。
首先同时提交 6 个请求：三个连接各一个普通调用、一个流式多轮调用，输出上限均为 16。
实际观察到 **4 个执行、2 个等待**，两个排队请求分别等待约 4.08、4.09 秒。
随后 DeepSeek 验证 1-token 输出上限；最后 MiMo 流在收到第一段文本后由客户端主动关闭，输出上限为 64。

| 连接 | 场景 | 输入 | 输出 | 上游总计 | 结果 |
| --- | --- | ---: | ---: | ---: | --- |
| MiMo / mimo-v2.6-flash | 并发普通 | 14 | 2 | 16 | 成功，约 79.71 秒 |
| DeepSeek / deepseek-flash | 并发普通 | 9 | 1 | 10 | 成功，约 4.08 秒 |
| 中转 / claude-sonnet-4-6 | 并发普通 | 12 | 5 | 17 | 成功，约 5.59 秒 |
| MiMo / mimo-v2.6-flash | 并发流式多轮 | 31 | 2 | 33 | 成功，约 4.08 秒 |
| DeepSeek / deepseek-flash | 并发流式多轮 | 20 | 1 | 21 | 成功，含排队约 6.21 秒 |
| 中转 / claude-sonnet-4-6 | 并发流式多轮 | 27 | 5 | 32 | 成功，含排队约 11.90 秒 |
| DeepSeek / deepseek-flash | max_tokens=1 | 15 | 1 | 16 | 成功，finish_reason=length |
| MiMo / mimo-v2.6-flash | 第一段文本后断开 | 未知 | 未知 | 未知 | cancelled/client_disconnected，约 0.54 秒 |
| **已知合计** | **7 次完整、1 次取消** | **128** | **17** | **145** | **缺少完整用量 1 次** |

MiMo 的一个慢请求没有阻止其他连接完成。此次没有真实网络超时或失败自动重试，也没有模型发现请求。
7 次完整结果的响应用量与 SQLite 记录逐项一致；取消请求的计数均为 null、usage_final=false，已释放名额和上游响应。
Selark 取消不证明供应商停止计算，取消请求的真实最终消耗无法据此得知。

[真实原始结果](api-stress-live.json) 保存模型、状态、排队时间、用量及身份核对结果，不保存提示词、回复正文或凭据。
[付费脚本](../scripts/verify_api_live_stress.py) 必须显式 `--execute`、指定三个连接与第二个现有客户端配置，
并创建排他的私有预算文件；每次请求前记账，最多 8 次，没有自动重试。
本次预算文件 `/tmp/selark-api-stress-real-budget-v041.json` 已使用 8 次；本轮不再追加真实请求。
