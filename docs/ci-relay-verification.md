## CI：已确认的问题、修复和证据

[原失败运行](https://github.com/nbcctwya/Selark/actions/runs/40844212546) 对应 `56a5154`。
3.11 和 3.13 通过；3.12 的 381 项单元测试、CLI 安装检查、进程恢复及 API 压力测试
也通过，失败发生在最后的四资源混合并发脚本：HTTPX 等待响应头时出现 `ReadError`。
该轮没有供应商真实请求，不能把它归因于 MiMo、DeepSeek、Kimi 或中转账户。

本地原脚本单轮通过，另作 30 轮、每轮 64 个客户端的观测也没有复现 ReadError。
已确认测试夹具有两个缺陷：

- 长寿命 HTTPX 池跨 CLI 子进程阶段复用连接；客户端默认空闲保留 5 秒，而测试服务器
  2 秒就关闭空闲连接。陈旧连接的时序竞争是待验证的诱因，不是已证明的原始根因。
- 首次异常后的清理再次 `gather`，可能用次生传输异常覆盖原始失败，且缺少当轮容量证据。

修复提交：[53964d3](https://github.com/nbcctwya/Selark/commit/53964d32e8d4a1a23c127492a2b4b98f2c3d6701)。
每个并发轮次使用独立连接池；客户端空闲保留缩为 0.5 秒；清理等待全部任务结束并保留
首次异常。失败时保存阶段、每个客户端结果、容量与模拟上游计数，真实生成重试始终为零。
**没有降低 64 客户端压力、放宽容量断言，或将传输错误当成预期成功。**

Actions 将三个 socket 验收拆开，混合并发提升为 10 轮；无论成败都保留 JSON 诊断产物
7 天。新增三个回归验证正常轮次、注入 ReadError、首次异常加次生 ReadError，保证错误
确实导致失败、全部任务收尾，并且不重试生成。

[修复后的绿色运行](https://github.com/nbcctwya/Selark/actions/runs/40849968719)：
三种 Python 均通过 384 项测试；3.12 的进程恢复、API 压力和十轮混合并发也通过。
本地固定版混合验收通过 668 个 HTTP 对话请求、14 个 CLI/示例调用；产生 140 次模拟

真实生成硬上限为 8 次，实际恰好 8 次；另有一次只读模型列表查询，返回 200 和原有
8 个模型，没有刷新持久配置，也没有逐模型生成。其他三种连接本轮真实调用为 0。

全部生成经过临时本机 Selark HTTP 服务、原有鉴权、并发控制和持久账本。
探测程序仅在进程内对两次明确的协议/参数对照覆盖适配设置，退出后销毁：
`max_completion_tokens` 对照，以及同一中转地址的 `/v1/messages` 对照。
没有改写连接配置，没有转向其他供应商或更贵模型，没有自动重试。

## 三类历史故障的定向结论

历史基准仍以 [应用场景报告](application-live-verification.md) 为准：中转 27 次尝试中
8 次完成，7 次协议错误、7 次超时、3 次 HTTP 400、2 次主动取消。19 条未取得用量的旧
记录继续保持未知，没有用本轮成功结果覆盖历史失败。

1. **HTTP 400：本轮未复现。** 原输出上限 32 的请求及当前两种输出参数均成功。
   之前收到的正文仅说明其上游 `bad response status code 400`，未提供可靠的无效字段
   指示。证据不支持直接归咎于固定参数、无效 Key 或永久不存在的模型；也无法排除某次
   内部路由、账户或上游服务问题。Selark 继续将上游 400 明确映射为 502 / upstream_rejected。
2. **超时：历史上卡在等待上游响应头阶段。** 七条记录的错误消息来自适配器发送请求后
   等待响应头的读取超时路径，`upstream_status` 均未知；不是已经收到 SSE 后的解析错误。
   本轮极短普通请求仍可等待约 28–29 秒，聊天场景等待响应头约 32 秒。
   使用既有环境代理的 HTTPX 分段观测显示主要时间在请求体发送完成之后；无法进一步
   拆分代理外部网络、中转排队与实际模型处理。未擅自延长 60 秒读取超时或 120 秒总时限。
3. **协议错误：只能确认当时 HTTP 200 的普通响应未通过协议校验。** 七次均为非流式，
   旧日志没有保存响应原文，因此无法倒推出具体缺失字段。原聊天场景本轮已经通过；
   gzip JSON、正常文本 choice、结束原因、SSE 独立用量帧和 DONE 均可解析。
   不应为了“通过”而放宽解析、把错误 JSON 当回答，或将未知用量记零。

尚需中转运营方用当时的时间与请求记录核对内部路由。可供定位的 Selark 记录示例
（时间为 UTC，站点内部请求 ID 与 Selark ID 不相同）：

| 类型 | UTC 时间 | Selark 请求 ID |
| --- | --- | --- |
| HTTP 200 协议错误 | 2026-10-29 05:57:18 | 6616ad750a6c43b7887174309558cdfa |
| 等待响应头超时 | 2026-10-29 06:05:19 | e0b21542630c473c8647e3f9e77ea5df |
| 极短请求 HTTP 400 | 2026-10-29 06:22:34 | d93d6603650c446e954b0312741d7681 |

本轮逐请求 JSON 另保留实际收到的 `x-oneapi-request-id` / `x-request-id`，便于对照
当前成功路由。没有代用户联系运营方，也没有进行管理端、账户或额度接口猜测。
