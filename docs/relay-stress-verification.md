# 中转站深入压力与协议对照

2026-10-30，Selark 0.7.2。用户明确授权加大中转站测试，并放宽费用约束。
**本轮完成 256 次真实生成调用：并发承载和取消恢复正常，但默认模型的参数控制与内容
遵循存在可重复的缺陷。不能把 HTTP 200 当作接入验收通过。**

脱敏统计见 [relay-stress-verification.json](relay-stress-verification.json)，可复用脚本见
[verify_relay_stress.py](../scripts/verify_relay_stress.py)。原始出站参数、响应、请求标识和
账本保留在 Git 忽略的 `.private/` 中，此报告不含中转站地址、Key 或账户标识。

所有请求均使用原有 Key 和允许模型，原配置、默认连接及运行时代码未修改。

主要深测模型为默认 `claude-sonnet-4-6`。另外七个模型用于短字符串及算术题的普通、

## 输出上限：61 次明确违反，切换协议没有解决

原提示要求输出 1 至 1000 的整数。下面 52 次全部返回同一完整数字序列，报告输出
**1,623 tokens**、可见内容 3,892 字符，结束原因为 `stop`。

| 路径 | 请求输出上限 | 普通 / 流式合计 | 超限 |
| --- | --- | ---: | ---: |
| Selark → Chat Completions，`max_tokens` | 1、8、32、128 | 8 | 8 |
| Selark → Chat Completions，`max_completion_tokens` | 1、8、32、128 | 8 | 8 |
| 直接 Chat Completions，两种参数 | 1、8、32、128 | 16 | 16 |
| 原生 Messages，版本 `2023-06-01` | 1、8、32、128 | 8 | 8 |
| 原生 Messages，版本 `2026-10-21` | 1、8、32、128 | 8 | 8 |
| 两种 Chat Completions 参数，较长输出 | 1,024 | 4 | 4 |

16 组直接请求与 Selark 出站请求的正文 **逐字节 SHA-256 相同**。这把已观察到的
输出上限异常定位到 Selark 以外的中转及其上游处理链路；仅更换本地参数名或 Messages
协议，本轮没有得到遵守上限的组合。

为避免只依赖一个重复提示，补充了 8 个不同起止数字的新提示，输出上限分别为 1 或 8。
7 次完整响应报告了 79–128 个输出 tokens，另 1 次成为 `upstream_protocol_error`。
最后两次直接复查也分别在上限 8 和 1 时报告 128 个输出 tokens。

因此共有 **62 个输出上限用例：61 次有明确超限用量，1 次未取得可用最终用量**。
没有把未知用量算成“遵守上限”，也没有把 `finish_reason=length` 单独当作通过：即使
结束原因为 `length`，实际报告 128 而请求上限仅 1，仍是超限。

## 系统消息、停止词和内容遵循

系统消息要求固定回复 `SYSTEM_OK`，用户消息只说“Please answer now.”。主矩阵 2 次和
补充对照 8 次均未遵守，实际返回了询问用户任务的普通回复。补充对照覆盖普通、流式、
直接 Chat Completions 和两版 Messages。出站请求保留了相应的 `system` 内容。

停止词补充对照要求返回 `ALPHA OMEGA TAIL`，同时设置 `stop="OMEGA"`；原生 Messages
发送对应的 `stop_sequences`。8 次全部返回完整字符串，停止词及其后的内容仍在。
主矩阵另有一次流式结果保留了 `<END>` 停止词；另一次普通请求返回拒绝语，单独记为
内容偏差，不把它当作停止词已被执行的证据。

其他内容结果：

- 中文精确回复、算术、JSON、排序、显式多轮历史和文本分块输入：主矩阵 12 / 12 正确。
- 两档长参考输入的取值检查：普通及流式共 4 / 4 正确；实际出站请求体约 4.5 KB 和 17.8 KB。
- 4 次慢速读取均完整交付。
- 单并发阶段的一次短字符串回复多出一个 `|`，其余该阶段回复正确。

| 请求模型 | 短字符串普通 / 流式正确数 | 算术普通 / 流式正确数 |
| --- | ---: | ---: |
| `claude-opus-4-6` | 2 / 2 | 2 / 2 |
| `claude-opus-4-7` | 2 / 2 | 2 / 2 |
| `claude-opus-4-8` | 2 / 2 | 2 / 2 |
| `claude-opus-5` | 2 / 2 | 2 / 2 |
| `claude-opus-5-5` | 2 / 2 | 2 / 2 |
| `claude-sonnet-4-6` | 2 / 2 | 2 / 2 |
| `claude-sonnet-5` | 2 / 2 | 2 / 2 |
| `claude-sonnet-5-5` | 0 / 2，均返回拒绝语 | 2 / 2 |

最后一个模型可完成普通算术，但本轮拒绝了指定无害短字符串的任务。所有上述响应的
模型 ID 与请求一致；API 自报 ID 不能证明底层实际模型身份，本轮未验证服务端路由。

## 并发、突发、取消和流式时序

并发逐级提升至 1、2、4、8、16。通过出站发送到响应头返回的重叠区间，确认真实上游
请求峰值达到 16；不是仅创建了 16 个本地任务。16 路阶段的 32 次调用全部完成且内容正确。

| 阶段 | 完整响应数 | 端到端 P50 | 端到端 P95 |
| --- | ---: | ---: | ---: |
| 1 路 | 2 | 7.21 s | 7.92 s |
| 2 路 | 4 | 7.72 s | 8.17 s |
| 4 路 | 8 | 7.03 s | 8.77 s |
| 8 路 | 16 | 7.32 s | 11.73 s |
| 16 路 | 32 | 7.40 s | 8.46 s |
| 64 客户端突发中的成功请求 | 32 | 11.21 s | 16.10 s |

这是一次短时、有界的实际观测，不能用于承诺长期吞吐或 SLA。突发阶段观察到 16 个
执行槽和 16 个排队槽；另 32 个请求被 Selark 返回 `429 / server_overloaded`，未发送
供应商。这些是本机按设计拒绝，不能记作中转站限流或失败。

4 次在等待响应头期间主动取消，4 次在流式首段正文后取消；随后 8 次恢复调用全部成功
且内容正确。8 次取消均只有一次上游尝试，最终用量未知。最后 active、queued、admitted、
pending 均归零，账本恢复计数全部为 0。主矩阵健康检查没有失败，最大耗时 150.56 ms。

8 次直接请求的长数字流式样本，首段正文等待 **15.53–16.46 秒**，其余全文在
**91–287 毫秒**内收到。该组样本的等待主要发生在首段之前；无法仅凭客户端时间确定
缓冲位于代理、中转、上游服务还是模型推理过程，也不能推广为所有流式请求的行为。

## 非文本错误、空正文与用量

补充矩阵的一次普通请求被网关拒绝为 `502 / upstream_protocol_error`，具体提示为
“上游返回了非文本回复”。它的上游 HTTP 状态为 200，原始异常正文未被保存，最终用量
保持未知。随后使用同一请求正文直接访问中转，得到可解析的文本与推理字段；首次非文本
错误没有再次复现，原因仍未确定。

另一次直接流式复查只有 `reasoning_content`，无可见正文，最终收到 `length` 和
128 个输出 tokens，尽管请求上限为 1。这里只保留字段类型和字符数量，没有保存推理
正文。这确认至少该次空正文已经存在于上游响应中。

同一个几十字符短提示重复 12 次，普通与流式各自模式内的出站正文完全相同，但中转
报告的输入从 **9,115 到 14,339 tokens** 不等。账本按原样保留报告数字；这些数字的
组成和计费含义需要运营方核对，无法凭客户端响应确定。

247 次有效完整响应的报告字段合计：

| 字段 | 合计 |
| --- | ---: |
| 输入字段 | 608,745 |
| 输出字段 | 87,387 |
| 上游明确提供的 `total_tokens` 字段 | 623,127 |

24 次原生 Messages 完整响应没有提供 `total_tokens`，保留其输入、输出字段但不伪造
总量，因此三行不能直接互相相加核对。缓存计数不再次叠加。另有 8 次取消与 1 次非文本
错误的最终用量未知；未查询账单或余额，无法给出本轮实际金额。

## 账本复核、脚本与复现

两轮临时账本共 234 条记录、234 次上游尝试；加上 22 次直接请求，恰好对应 256 次生成。
230 条有返回请求 ID 的记录逐条核对调用方绑定和已报告用量；其余 4 次响应头前取消，
按同一临时调用方的其他记录离线匹配确认。无重复记录、自动重试或遗留待落账。

初版压力脚本误把 32 个入口过载拒绝列为“账本缺失”。按既有设计，这类拒绝只记请求
日志，不建立调用记录，见 [API 压力验收](api-stress-verification.md)。已修正核对范围，
离线复核原始证据后，无实际缺失；原报告保留，修正结果单列在脱敏 JSON 中，没有为修正
统计口径重跑付费用例。

新增 13 项离线脚本回归，覆盖发送前次数预留、目标与凭据约束、无重试、停止标记、
Retry-After、两套完整矩阵的参数准备、超限分类及过载拒绝与实际丢账的区分。
本轮没有更改运行时解析规则来把异常响应变成成功。

最终 Python 3.12 全量离线回归 **572 项通过**（68.49 秒），Ruff 检查、格式检查和
Git 差异检查通过。156 个发布候选文件的既有凭据精确匹配与常见密钥格式扫描未发现匹配；
三组原始报告均确认被 Git 忽略。原有配置未修改，临时服务、调用方与数据库已清理。

主矩阵与定向对照都需要显式执行，会产生新的付费请求：

```bash
PYTHONPATH=src .venv/bin/python scripts/verify_relay_stress.py \
  --execute --work-dir .private/relay-full-new-run

PYTHONPATH=src .venv/bin/python scripts/verify_relay_stress.py \
  --execute --suite controls --max-requests 40 \
  --work-dir .private/relay-controls-new-run
```

默认主矩阵要求连接中有本轮的 8 个允许模型，最大 256 次尝试；定向矩阵为 40 个用例。
工作目录必须全新，出站前持久记录次数，失败不退还；支持工作目录内的 `STOP` 标记。
测试按本轮用户授权继续收集输出超限证据，原四 API 小额验收脚本的超限自动停止保护
继续保留。真实脚本不加入 CI，CI 只执行离线回归。

当前最值得运营方核查的是：协议转换过程中 `system`、`stop` / `stop_sequences` 和输出
上限是否被丢弃或覆盖，以及输入计数的来源。客户端证据支持这些排查方向，尚不能确认
其具体服务端实现，也没有验证可修复这些问题的配置组合。
