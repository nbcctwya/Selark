日期：2026-10-29；环境：WSL/Linux，当前用户 pipx 安装的 Selark 0.6.1。
本轮按用户要求扩大真实测试，与此前 [8 次短请求验收](resource-live-verification.md)
及 [模拟压力测试](resource-simulation-verification.md) 分开计数。

全部生成都经过实际 Selark HTTP 服务，调用已配置的真实上游，没有模拟响应。

## 并发、真实故障与资源释放

前两批各发起 6 个客户端请求，均观测到 **4 个执行、2 个排队**。第一批全部完成，排队的
两条中转请求分别等待约 3.06 和 3.58 秒。第二批一个 DeepSeek 编程请求等待约 10 秒后
返回 503 / `queue_timeout`，落账 `upstream_attempts=0`。确认未发送上游后，在空闲批次
显式另发一次请求补齐该编程场景；这不是重复付费生成或自动重试。

另外两批四客户端请求均观测到执行峰值 4；后续有三路并发和逐个执行。
整个普通 API 测试共采样 1,550 次 `/health`，失败 0 次，最大观测耗时 15.91 ms，未观测到
存储降级。最终活动数、排队数均为 0，pending 和损坏收据均为 0。
服务进程的 Linux 内存高水位为 64,500 kB，结束时 RSS 为 32,064 kB；这只是本次进程观测，
不包含测试客户端，也不构成所有负载下的内存上限保证。

中转长代码审查请求 `d3b2e670bfdd482b93e93f38691323fa` 在返回部分文本后收到上游错误事件：

- HTTP 已开始为 200，但流没有成功结束，客户端识别 `upstream_protocol_error`。
- 记录为 `status=failed`、`upstream_result=failed`、`delivery_status=sent`；后者指错误事件
  已向下游交付，不表示完整答案交付成功。
- 上游没有给出最终用量，输入/输出/总量均为 `null`。Selark 保留 `unknown_hold`，其
  74,702 Token 配额预留是原有算法的保守估算，不是已确认消耗。
- 槽位释放，后续请求继续运行；没有重发该生成，重启后未知状态和预留仍然保留。

本轮没有保留或转发供应商原始错误详情，无法确定中转内部故障的具体原因。

## 内容结果与发现的问题

按上述明确的结构、字段和可执行检查：**24 条通过、7 条不通过、2 条不评估**。
不评估的两条是本地排队拒绝和上游断流。以下全部保留原始失败结果，后续修正单独计数：

1. **DeepSeek 长文首轮返回非法 JSON**，尾部多出字符；后续两轮返回有效 JSON，目标字段一致。
2. **中转代码存在半开区间差一错误**：把间隔写成 `next_start - previous_end - 1`。
   703 项检查失败 97 项；反馈最小案例后，修正版本全部通过。
3. **DeepSeek 设计首轮对象结构不符合要求**：四个屏幕在语义上存在，但缺少每个对象要求的
   `id` 字段；还出现“中断后重试不计费”的不可靠表述。下一轮反馈后结构修正，最终设计
   明确保留未知消耗与手动恢复约束。
4. **MiMo 设计首轮 JSON 字符串中的引号未转义**；下一轮具体指出后修正。
5. **中转设计首轮和 MiMo 设计第三轮到达 2,048 Token 上限**，均保留 `length` 和完整实际用量，
   但 JSON 截断，不能作为合格结构化结果。中转下一轮缩短表达后完成；MiMo 额外使用 4,096
   上限并由客户端提供明确的已确认约束摘要后，返回完整有效结果。
6. **Kimi 首轮 512 上限没有留下代码输出空间**：输出 512，思考 509，最终正文为空，
   `finish_reason=length`。它是已正常结束并计量的生成，但编程任务未完成。原样保留实际
   思考历史、缩短后续指令后，手动续写得到完整函数。

共对 **9 个实际返回的函数实现**执行 **3,456 项检查**，其中上述错误版本失败 97 项；
其他 8 个实现均通过。没有执行任意模型程序：先检查 AST 和调用白名单，再在独立进程中
使用受限 builtins、禁用导入/I/O、限制 CPU/内存/文件写入。Kimi 首轮没有函数，不计入这 9 个。

设计验收也修正了测试器的两项过窄假设：原提示未限定线框必须是单个字符串、状态集合
必须是数组，因此接受文本行数组，以及含所需 `id` 字段的对象值集合。仅重评本地保存的
回答，没有因此增加 API 调用；JSON 结果保留初评及修订说明。屏幕对象缺少明确要求的 `id`
仍然不通过，没有为了结果好看而补造字段。

代码审查与设计的“通过”只覆盖列出的确定条件。人工复核仍看到不严谨措辞，例如将一次
同步调用误描述成带 `await`，或把可能发生的竞态说成必然发生；不据此给模型做综合能力排名。
